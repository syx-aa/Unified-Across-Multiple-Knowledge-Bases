# 开发约束（本地项目 `检索页`）

本文件是开发过程中**必须遵守的约束清单**。
任何新增或修改约束，须经项目负责人确认。

> 与 SpecDD 流程配套：约束管「怎么做」，Spec 管「做什么」。

---

## R-01 · 降级决策规则　【最高优先级】

### 规则

功能开发中**任何形式的降级，都必须先停下来询问项目负责人，
得到明确选择后方可实施。**

严禁以下行为：

- 自行降级后再汇报（"我先关掉重排了，你看下"）
- 以"环境不支持 / 跑不动 / 太慢 / 装不上"为由默认降级
- 把降级路径悄悄写进代码，使主路径形同虚设
- 为了跑通测试而降低标准

### 什么算「降级」

| 类别 | 具体情形 | 本项目实例 |
|---|---|---|
| 功能降级 | 关闭或跳过某个环节 | 关掉重排、去掉向量路 |
| 实现降级 | 用简化实现替代完整实现 | 用规则匹配代替模型推理 |
| 依赖降级 | 换用精度更低 / 体积更小的模型或库 | torch → ONNX、fp32 → int8 |
| 路径降级 | 主路径不可用时静默回退 | 服务端 → 本地两路（SPEC-014） |
| 验收降级 | 放宽或跳过某条 AC | 删改测试用例使其通过 |
| 验证降级 | 以"应该没问题"代替实跑 | 不跑 `eval_backend.js` 就宣称达标 |

### 询问时必须提供的内容

一次合格的分叉询问须包含以下四部分，缺一不可：

1. **现状**：卡在哪一步，为什么需要降级
2. **可选方案表**（至少 2 个）：
   `方案名 / 具体做法 / 收益 / 代价 / 影响范围`
3. **量化影响**：对核心指标的影响（见 R-03 基线），
   **不能只说"会差一点"** —— 要给出具体数值或量级
4. **推荐方案 + 理由**

### 等候原则

负责人未明确选择前：

- **不得开始实施**任何降级方案
- 可继续推进与该决策无关的其它工作
- 若整条链路被卡住，应说明阻塞点并等待，不得自行其是

## R-02 · SpecDD 流程约束

**每个功能必须先有 Spec 与 AC，再有实现，最后由测试判定是否 Done。**

```
Spec → AC → Test → Implement → Verify
```

状态的判定权在 **AC + Test**，不在"我觉得写完了"。

两条硬规则：

1. **一动手写代码就把 Spec 挪进 `Indevelopment`** —— 不存在从 Plan 直接跳 Done
2. **有代码不等于 Done** —— 只要还有一条 AC 未验证，就停在 `Indevelopment`

详见 [`specs/README.md`](./specs/README.md)。

## R-03 · 验收基线（120 题评测集 `tests/eval_cases.json`）

| 档位 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| 纯前端 BM25 + 实体（历史起点） | 64.2% | 90.0% | 0.753 |
| 服务端融合，无重排（云端现版） | 72.5% | 93.3% | 0.816 |
| 服务端融合 + 重排（本地完整版） | 79.2% | 97.5% | 0.854 |

**任何改动合并前须满足**：总体 Hit@1 不降，且无题型 Hit@5 退步。

判定命令：`node tests/eval_backend.js`（需先 `python server.py` 起服务）。

> 本表同时是 R-01 第 3 条「量化影响」的参照基准 ——
> 说明降级影响时必须落到这些指标上。

## R-04 · 其它硬规则

1. **指标口径不可变** —— 评测口径、权重、阈值改动须单独建 Spec，
   不得夹带在功能改动里（否则历史数字失去可比性）。
2. **回归必须全绿** —— 改动后跑 `tests/` 下全部脚本，
   不能只跑与自己改动相关的那一个。
3. **降级路径必须可见** —— 系统自带的自动降级（如服务端不可达）
   要在界面上明确提示当前处于哪条链路（SPEC-029）。
   即：**自动降级可以存在，但必须让用户看见，且设计决策上的降级必须询问。**
4. **临时脚本用完即删** —— 调试/对比用的 `_tmp_*.js` 不留在仓库里。
