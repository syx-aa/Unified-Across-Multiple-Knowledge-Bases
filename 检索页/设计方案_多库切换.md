## 一、目标

现在页面只能检索**一个**知识库（世界杯）。本方案增加**知识库切换器**，
让用户在 `LLM Wiki/LLM Wiki/` 下的多个库之间切换，切换后检索范围、
实体/别名表、向量索引、答案来源全部限定在所选库内。

**边界（不做什么）**：不做跨库联合检索、不自动判断该查哪个库。

---

## 二、现状摸底（实测）

### 2.1 三个库都是「半成品」

| 库 | Raw | source | entity | concept |
|---|---|---|---|---|
| `2、小红书AI帖子` | 85（1963 KB） | 85（189 KB） | 25 | **0 字节** |
| `3、世界杯` | 72（1027 KB） | 72（147 KB） | 62 | **0 字节** |
| `4、企业内部项目文档` | 104（831 KB） | **无** | 125 | **43 字节** |

**entity / concept 目录里的文件全是 Obsidian 自动生成的空占位** ——
有文件名（即词条名），但内容为空。

### 2.2 当前页面读的不是这三个库

```python
ROOT = r"E:/课件/练习"          # ← 真正的数据源
#   Cleaned/  56 篇（199 KB）
#   entity/   62 个（50 KB）    ← 有内容
#   concept/  14 个（12 KB）    ← 有内容
```

`E:/课件/练习` 才是唯一词条页完整的库。三处格式还不一致：

| 来源 | 模板 |
|---|---|
| `E:/课件/练习/Cleaned` | `# 标题` + `> 抓取时间` + `## 📝 正文` + `## 🔑 关键要点` |
| `LLM Wiki/*/Wiki/source` | `> 原始帖子` + `## 📋 基本信息` + `## 🎯 核心主题` + `## 📌 关键要点` |

即 `LLM Wiki` 是**更新一版但未完成**的产物。

### 2.3 构建管线只有「打包」，没有「清洗」

`build/` 下 8 个脚本全是构建/向量化/导出，**没有任何清洗脚本**。
目录名 `LLM Wiki` 说明清洗这一步原本是靠大模型做的。

## 四、清洗方案（需定档位）

### 4.1 要补什么

现有词条页只有名字。清洗需补齐三样：

| 字段 | 来源 | 能否自动化 |
|---|---|---|
| `desc` 一句话描述 | 从 Raw 抽取该词条首次出现的上下文 | ⚠️ 规则抽取质量有限 |
| `refs` 关联笔记 | 扫 Raw 中所有 `[[词条]]` 反向索引 | ✅ 完全可自动化 |
| `count` 出现次数 | 统计 `[[词条]]` 出现频次 | ✅ 完全可自动化 |

另外 4 号库缺 `source/`（笔记正文），需由 `Raw/` 转换。

### 4.2 档位对比

| | 档位 A · 全自动 | 档位 B · 自动 + 人工审描述 | 档位 C · AI 逐条生成 |
|---|---|---|---|
| 做法 | 脚本扫 Raw，规则抽描述，全量生成 | 脚本生成后，你审一遍描述并修正 | 我逐词条写描述，逐篇转写笔记 |
| 词条总量 | 227（4 号）+ 50（2 号）+ 76（3 号）= **约 350 条** | 同左 | 同左 |
| 笔记转写 | 规则套模板 | 规则套模板 | 逐篇改写 |
| **耗时** | 分钟级 | 脚本分钟级 + 你审稿 | 很长（数百次生成） |
| **描述质量** | 低（可能是断句） | 中～高（你把关） | 高 |
| **对检索的影响** | 实体路只能靠标题匹配，**内容贡献近乎为 0** | 接近现有世界杯库水平 | 同上或更好 |

### 4.3 ⚠️ 必须说清的降级点

即使档位 B/C，新接入的库也**达不到现有世界杯库的水准**：

| 项目 | 现有世界杯库 | 新库 |
|---|---|---|
| 笔记清洗 | 人工/大模型逐篇整理 | 规则套模板 |
| 词条描述 | 大模型精炼的一句话 | 规则抽取或简写 |
| 分类导航 `index.md` | 有（人工整理） | 需新建 |
| **别名表** | 有（cr7 → C罗） | 需新建 |

**影响**：切到新库后，实体路与概念路的**内容匹配会明显弱于世界杯库**，
检索质量大概率低于现有的 79.2%。这是降级，按 R-01 需你确认。

## 五、切换功能设计（双路径）

按 Q2，两条路都要支持，实现不同：

### 5.1 起本地服务（完整能力）

```
前端切换器 → state.db 变更
              ↓
    /api/databases        列出可用库
    /api/search/stream?db=xxx   按库检索（三路 + 重排）
```

- 服务端启动时扫描 `vector/<db>/` 下所有库
- **懒加载**（决策 1-B）：默认只加载当前库，切换时再载入，避免启动变慢
- 切换 → 清空对话（Q4）

### 5.2 双击打开（能力受限）

- 每个库生成一份 `data-<db>.js`
- 切换时动态加载对应脚本
- ⚠️ 只有**关键词 + 实体两路**（无向量、无重排）
- ⚠️ 若 `file://` 下动态加载受限，需退化为「切换提示重启」

| | 双击 | 本地服务 |
|---|---|---|
| 检索路数 | 2 路 | 3 路 + 重排 |
| 基线 | 64.2% | 79.2% |
| 切换实现 | 多份 data.js | 服务端多库索引 |
