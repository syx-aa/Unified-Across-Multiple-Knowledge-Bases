# SPEC-016 浏览器端 transformers.js 向量推理

> 状态：Abandoned ｜ 原优先级：P0 ｜ 归属：检索层 ｜ 归档：2026-10-23

## 1. 原需求

设计方案 v2（第五节/第八节）：用 `transformers.js`（jsdelivr CDN）+ 本地
`bge-small-zh-v1.5` 的 int8 ONNX（24MB）在**浏览器内直接推理**，
首屏先用关键词可用，模型后台加载，就绪后自动开启向量路。

## 2. 为什么放弃

| 问题 | 说明 |
|---|---|
| 架构方向变了 | P3 后端化后检索整体搬进服务端（SPEC-013），模型推理统一在 Python 侧 |
| 首屏体积 | 24MB 模型拖慢首屏，需后台加载 + 降级等待逻辑，复杂度高 |
| `file://` 限制 | 本地双击打开无法 fetch 模型，必须起服务，与「双击即可用」目标冲突 |
| 双份实现 | 浏览器一套、服务端一套，两套向量逻辑难保证一致，评测口径分裂 |

## 3. 替代方案

**Python 侧推理**（`build/build_vectors.py` 离线编码 + `server.py` 在线查询编码）。
向量结果写入 `vector/vectors.json` 与 Chroma，前端只消费结果，不跑模型。

## 4. 残留痕迹

- [`build/export_onnx.py`](../../build/export_onnx.py#L25-L41) 仍导出 ONNX，但用途改为
  **服务端 ONNX Runtime**（云端无 torch 环境），不是给浏览器用。
- 前端降级链（[SPEC-014](../Done/SPEC-014_前端服务降级.md)）保证没有服务端时页面仍可用（走内置 BM25）。

## 5. 教训

「模型放前端」在演示场景很诱人（零部署），但一旦引入服务端，
它就是**重复实现**。放弃它是 P3 后端化能落地的前提。
