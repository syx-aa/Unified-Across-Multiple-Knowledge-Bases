# SPEC-032 检索过程逐步实时显示

> 状态：Done ｜ 优先级：P1 ｜ 归属：前端 + 服务端 ｜ 类型：功能改进

## 1. 需求（Spec）

用户要求：检索过程**进行到哪一步就显示那一步**（进行到分词就出现「分词」）,
而不是等全部跑完一次性把整个 trace 抛出来。

现状：`server.py` 的 `search()` 是同步函数，按序跑完
（分词 → BM25 → 实体 → 向量 → 融合 → 重排）后一次性返回 `trace` 数组；
前端 `composeAnswerServer()` 拿到结果才第一次写 `OUT`。
所以服务端检索那约 10 秒（重排占大头）里，界面上没有任何新进展。

SPEC-031 只补了"检索中"的静态提示，本 Spec 要做的是**真实的逐步推进**。

## 2. 验收标准（AC）

- [x] AC1：服务端每完成一步就推送一次，前端**立即**渲染该步
- [x] AC2：新增流式接口 `/api/search/stream`（NDJSON，每行一个 JSON 对象）
- [x] AC3：原 `/api/search` 一次性接口**保留**，流式不可用时自动回退，不报错
- [x] AC4：逐步渲染过程中 trace 面板不闪烁、可正常展开/收起
- [x] AC5：与 SPEC-030 的序号机制兼容 —— 过期请求停止渲染
- [x] AC6：全部完成后正确显示「共 N 步 · 检索耗时 X ms」
- [x] AC7：`tests/test_progress_feedback.js` 第 1、3 组覆盖逐步推送与流式输出
- [x] AC8：现有测试全部通过（回归）

| 文件 | 位置 | 说明 |

## 5. 验证结果（Verify）

实测（2026-10-24），mock 服务端逐步推送（每步间隔 150ms）：

| 用例 | 结果 |
|---|---|
| 提问后 30ms（服务端尚未返回） | 已显示「✦ 检索中 · 正在检索「梅西是谁」的资料」 ✅ |
| 逐步推送过程 | 界面刷新 6 次，「已进行 N 步」从 1 递增到 5 ✅ |
| done 之后 | 换成完整 trace「共 8 步 · 检索耗时 118.00 ms」，答案区建立 ✅ |
| 流式中途 | 答案区已含部分内容 `<p class="lead">梅<span …` ✅ |
| 流接口 404 | 自动降级本地两路，结果正常 ✅ |
| 抢占提问 | 立刻接管界面，旧问题提示无残留 ✅ |

回归全绿（8 个脚本）。

**顺带发现**：真实服务端的耗时分布是
分词/关键词路/实体路/向量路 ≈ 0.06s，重排 ≈ 9.13s ——
三路检索几乎不耗时，慢的几乎全是重排。
