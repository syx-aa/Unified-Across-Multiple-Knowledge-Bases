# SPEC-030 重复提问/快速切换的竞态修复

> 状态：Done ｜ 优先级：P1 ｜ 归属：前端 ｜ 类型：缺陷修复

## 1. 需求（Spec）

两个现象，同一根因 —— **请求没有序号，旧请求的异步回调照样写 DOM**：

| 现象 | 触发方式 |
|---|---|
| 页面卡住 | 快速连点「智能 / 关键词 / 实体」 |
| 看不到生成进度，答案要等全部完成才一次性出现 | 在上一次生成未结束时再次提问 |

链路上的三个缺口：

1. `index.html:1296` —— 模式按钮每次点击都 `if(state.q) ask()`，
   立刻重跑「检索 + 大模型生成」。服务端单次检索约 10 秒（含重排），
   连点 N 次即发起 N 个并发请求，服务端排队、页面状态互相覆盖。
2. `index.html:881` —— `busy.abort()` 只中止 fetch，
   被中止的流进入 `catch` 后仍执行 `renderAnswer()`，把整个 `OUT` 覆盖掉，
   表现为「进度消失 / 界面跳变 / 只剩最后一个答案」。
3. `composeAnswerServer()` 的 `.then` 没有任何过期判断，
   谁先返回谁写界面，晚到的旧结果会盖掉新结果。

## 2. 验收标准（AC）

- [x] AC1：每次 `ask()` 分配递增的唯一序号，捕获进闭包
- [x] AC2：过期请求在**所有异步恢复点**（服务端 `.then`、流循环每一帧、`catch`、`finally`）
      检查序号，不等即静默返回，**不写任何 DOM**
- [x] AC3：连点模式切换 N 次，最终界面只呈现最后一次的结果
- [x] AC4：流式过程中被新提问取代时，旧流停止写入且**不触发** `renderAnswer()` 覆盖
- [x] AC5：`busy` 只在仍是最新请求时释放，不误清空新请求的控制器
- [x] AC6：新增 `tests/test_concurrent.js` 覆盖 AC1-AC5
- [x] AC7：现有测试全部通过（回归）

## 3. 测试用例

| 用例 | 场景 | 期望 |
|---|---|---|
| TC1 | 快速连点 3 次模式 | 只渲染第 3 次结果 |
| TC2 | 第一次还在流式时再次提问 | 旧流不覆盖界面，进度正常显示 |
| TC3 | 旧流被 abort | 不调用 `renderAnswer()`，无错误提示 |
| TC4 | 慢请求后到 | 被丢弃，不覆盖已显示的新答案 |
| TC5 | 回归 | 4 个现有测试全绿 |

## 4. 实现

| 文件 | 位置 | 说明 |
|---|---|---|
| [`index.html`](../../index.html#L920-L923) | `REQ` | 新增全局提问序号 |
| [`index.html`](../../index.html#L881-L897) | `ask()` / `handleAnswer()` | 分配 `seq`；服务端返回后先校验再渲染 |
| [`index.html`](../../index.html#L1074-L1142) | `streamAnswer()` | 签名加 `seq`；流循环每帧、`catch`、`finally` 均校验 |

过期判定的统一写法：`if(seq !== undefined && seq !== REQ) return;`
（`seq` 可缺省，保证直接调用 `handleAnswer` 的旧路径不受影响）

## 5. 验证结果（Verify）

实测（2026-10-24）：

| 场景 | 结果 |
|---|---|
| 连点三次（模拟快速切换模式） | 发起 3 次生成，界面只剩第 3 次答案，前两次内容无残留 ✅ |
| 慢旧流吐字中被抢占 | 呈现最新答案，陈旧内容即便继续吐出也不再写回 ✅ |
| 过期流被 abort | 不触发 `renderAnswer()` 兜底，界面无错误文案 ✅ |
| busy 释放 | 后续提问正常，无卡死 ✅ |

**注**：修复只解决浏览器侧的竞态。服务端那边被中止的请求仍会在 Python 侧跑完
（单次含重排约 10 秒），只是结果不再回流到界面 —— 这是可接受的取舍，
若要真正省算力，需在服务端加请求取消，属另一个议题。
